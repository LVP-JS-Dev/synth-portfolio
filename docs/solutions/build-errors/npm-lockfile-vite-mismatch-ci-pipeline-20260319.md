# Troubleshooting: npm Lockfile Incompatibility and Vite/Vitest Type Mismatch in CI

## Problem

CI pipeline failed three consecutive times after pushing PR #6 changes due to cascading dependency issues: first, platform-specific rollup binaries missing because the lockfile (v3, generated by npm 11 on macOS/Node 25) was incompatible with CI's Node 20 npm; then, after regenerating the lockfile, a TypeScript type conflict surfaced because `@vitejs/plugin-react@4.7.0` pulled `vite@7` while `vitest@1.6.1` pulled its own nested `vite@5`.

## Environment

- **Framework**: Next.js 16 (App Router)
- **Language**: TypeScript (strict mode)
- **Test Runner**: Vitest (v1.6.1 → upgraded to v3.2.4)
- **Build Tool**: Vite 7.3.1 (via `@vitejs/plugin-react@4.7.0`)
- **Local Runtime**: Node 25.8.1, npm 11.11.0 (macOS ARM64)
- **CI Runtime**: GitHub Actions ubuntu-latest, initially Node 20, then Node 22
- **Package Manager**: npm with lockfile v3
- **Date**: 2026-03-19

## Symptoms

- `npm test` in CI crashes immediately with: `Error: Cannot find module @rollup/rollup-linux-x64-gnu`
- `npm run typecheck` fails with: `vitest.config.ts(6,13): error TS2769: No overload matches this call`
- TypeScript reports incompatible `Plugin<any>` types between `node_modules/vite/` and `node_modules/vitest/node_modules/vite/`
- All local checks pass (typecheck, lint, test, build) — failure is CI-only

## What Didn't Work

**Attempted Solution 1:** Update CI Node version from 20 to 22 LTS

```yaml
# .github/workflows/ci.yml
- node-version: 20
+ node-version: 22
```

- **Why it failed:** The lockfile was generated by npm 11 (Node 25). Even Node 22's npm 10 couldn't correctly resolve the cross-platform optional dependencies from a lockfile generated by a newer npm major. The `@rollup/rollup-linux-x64-gnu` entry existed in the lockfile but `npm ci` still failed to install it.

**Attempted Solution 2:** Regenerate lockfile only (without upgrading vitest)

```bash
rm -rf node_modules package-lock.json
npm install
```

- **Why it partially failed:** This fixed the rollup platform binary issue — `npm ci` on Node 22 now correctly installed linux-x64 binaries. However, it exposed a latent type conflict: the fresh lockfile resolved `@vitejs/plugin-react@4.7.0 → vite@7.3.1` (hoisted) alongside `vitest@1.6.1 → vite@5.4.21` (nested). Two different `Plugin<any>` type definitions caused `tsc --noEmit` to fail on `vitest.config.ts`.

## Solution

Three changes applied incrementally, each committed separately:

### Step 1: Update CI to Node 22 LTS

```yaml
# .github/workflows/ci.yml
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22  # was: 20
          cache: npm
```

### Step 2: Regenerate lockfile for cross-platform compatibility

```bash
rm -rf node_modules package-lock.json
npm install
```

### Step 3: Upgrade vitest v1 → v3 to unify vite version

```bash
npm install --save-dev vitest@^3
```

Verification after all three steps:

```bash
$ npm ls vite
synth-portfolio@0.1.0
├─┬ @vitejs/plugin-react@4.7.0
│ └── vite@7.3.1
└─┬ vitest@3.2.4
  ├─┬ @vitest/mocker@3.2.4
  │ └── vite@7.3.1 deduped
  ├─┬ vite-node@3.2.4
  │ └── vite@7.3.1 deduped
  └── vite@7.3.1 deduped       # single version, fully deduped

$ npm run typecheck  # ✅ clean
$ npm run lint       # ✅ clean
$ npm test           # ✅ 25/25 passed
# CI: both push and PR triggers green
```

## Why This Works

1. **Rollup platform binaries**: npm lockfile v3 from npm 11 uses a slightly different resolution format for `optionalDependencies`. When `npm ci` runs on npm 10 (Node 20/22), it may fail to resolve platform-specific optional packages that were recorded by npm 11. Regenerating the lockfile from `npm install` on the same npm version (or one that can correctly read the v3 format) ensures all platform variants are properly listed and resolved.

2. **Vite version deduplication**: `@vitejs/plugin-react@4.7.0` declares `vite@^6.0.0 || ^7.0.0-0` as a peer dependency and installs `vite@7.3.1`. `vitest@1.6.1` has `vite@^5.0.0` as a dependency and installs its own nested `vite@5.4.21`. TypeScript sees two different `Plugin<any>` type definitions (one from each vite version) and reports them as incompatible when `react()` plugin is passed to `defineConfig()`. Upgrading vitest to v3 changes its vite peer dependency to `^6.0.0 || ^7.0.0-0`, allowing npm to deduplicate to a single `vite@7.3.1` — one type definition, no conflict.

3. **Why the three fixes are interdependent**: Node version alone doesn't fix the lockfile format mismatch. Regenerating the lockfile alone surfaces the vite conflict (because fresh resolution picks latest compatible versions). The vitest upgrade is the final piece that aligns the entire vite ecosystem under one major version.

## Prevention

1. **Pin Node version with `.nvmrc` + `engines` field in `package.json`**: Add `.nvmrc` containing `22` to the repo root. In `package.json` add `"engines": { "node": ">=22", "npm": ">=10.9" }`. CI should read `.nvmrc` explicitly via `node-version-file: .nvmrc` in the `actions/setup-node` step. This creates a single source of truth that both local devs (`nvm use`) and CI consume, eliminating the lockfile format mismatch at the source.

2. **Run `npm ls vite` as a post-install guard in CI**: After `npm ci`, add a step that runs `npm ls vite --depth=0` and fails if more than one distinct major version appears. This catches vitest/plugin-react vite splits before tests even start.

3. **Never commit a lockfile generated by a different npm major than CI uses**: If local Node is ahead of CI, either align CI to match or regenerate the lockfile in a CI-compatible environment before committing. Document the required Node/npm version in `CONTRIBUTING.md`.

4. **Add Renovate/Dependabot grouping for the vite ecosystem**: Group `vite`, `vitest`, `@vitejs/plugin-react`, and `@vitest/*` into a single update PR so version incompatibilities surface in isolation, not mid-feature PRs.

5. **Use `npm ls <pkg>` locally before pushing lockfile changes**: After any dependency change, run `npm ls vite` (and other key packages) to verify deduplication. Multiple major versions in the tree is a red flag.

6. **Add lockfile version assertion in CI**: Before `npm ci`, validate `lockfileVersion` matches expectations: `node -e "const l=require('./package-lock.json');if(l.lockfileVersion!==3)process.exit(1)"`. Fail fast on format mismatches.
